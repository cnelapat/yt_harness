## Context

`prove_red_or_die` refuses approval only when *every* acceptance command passes. Any
non-zero exit is accepted as the red proof and recorded in the lock as evidence the
frozen test has teeth.

It is not that evidence. A greenfield ticket's module does not exist at approve time, so
its acceptance commands fail during collection — the test never runs, and no assertion
in it is ever executed. What the lock records is that an import failed.

This is not a forward-looking gap. Every red proof this repo has taken is that shape: 54
of them across T001-T005, exit code 2 where the command names a file and 4 where it
names a node id, and exit code 1 nowhere at all. Confirmed against pytest directly
rather than inferred — a whole-file command whose module is absent exits 2 and reports
`ERROR <file>`; the same with a `::node_id` selector exits 4; only a command that reaches
an assertion exits 1 and reports `FAILED <file>::<test>`. So the frozen tests guarding
this harness, including the ones guarding the gate itself, have never been shown to have
teeth.

T003 already states the principle that condemns this, and enforces it for the
characterization tier: a vacuous test never runs, so the worst it can produce is `ERROR`,
and requiring `FAILED` at a declared node id separates a test with assertions from one
without, which confinement and exit codes cannot. The red proof still judges on exit
codes.

`prove_red_or_die` also has no tests of its own today. It is referenced once in the
suite, at `tests/test_gate_mutation.py`, only to be monkeypatched out. This ticket brings
its first ones.

## Goal

A red proof must have teeth, not merely be red. Every pytest acceptance command must
produce a pytest `FAILED` naming a node id inside one of the ticket's frozen files;
`ERROR` is never sufficient, and a command that produces no `FAILED` of its own is named
in the refusal rather than carried by a sibling that did. Non-pytest commands still run
and still count toward redness, but cannot supply the detection, and an acceptance set
containing no pytest command able to supply it is refused rather than exempted.

The matcher is `detected_node_ids` unchanged — same function, same frozen-file
membership test — so no new ticket field is added. The mutation tier needs `expects`
because it must pin *which* test catches a given perturbation; the red tier has no
perturbation to attribute, so frozen-file membership is the whole rule.

In practice the author lands importable signature stubs in `scope` before approve, which
turns the greenfield shape from `ERROR <file>` into `FAILED <file>::<test> -
NotImplementedError`. A test that asserts nothing then goes green instead, and the
existing refusal catches it.

Each `red_proof` entry then carries `detected_by` — the same field name the mutation
proof already stores — and `report()` reads that stored field rather than re-deriving a
tier. A lock lacking the field is displayed as a pre-amendment import-only proof whose
teeth were never verified, on the strength of the absence.

## Before approving

`tests/test_gate_red_proof.py` does not exist. Author this ticket's 9 tests — D15, D16,
D17 and D20 — before running `approve`, and no others: a test for later work is a
`full_gate` failure this ticket's baseline cannot absorb.

Approve runs against the *current* `prove_red_or_die`, which still accepts any non-zero
exit, so the old bar applies to this ticket's own approval. Land importable stubs for
the new names in `edad/gate.py` first all the same, so the red run reports `FAILED` at
the frozen node ids rather than `ERROR` on a missing attribute — this ticket should meet
the bar it ships.

## Required interface

All in `edad/gate.py`.

- `detected_node_ids(output, frozen)` is reused verbatim. Do not add a second matcher and
  do not change its signature: `tests/test_gate_mutation.py` freezes its behaviour, and
  a change there is a frozen-hash failure in a file this ticket may not write.
- `_supplies_detection(command)` is reused verbatim for the pytest/non-pytest split.
- `prove_red_or_die(root, ticket, commands)` keeps its existing refusals — the timeout
  refusal and the all-commands-pass refusal — and gains two more, in this order. First:
  when no command in the acceptance set can supply detection, refuse and say so. Second:
  when a pytest command produced no `FAILED` at a node id in a frozen file, refuse and
  name that command. Refuse on the union of offenders, not the first — an author who
  fixes one command at a time learns of the next only on the next approve.
- The red proof's detection is per command. A `FAILED` reported by one command does not
  discharge another: on T005's 12 commands that would prove one test has teeth and leave
  11 unexamined, the shape D6 rejected for `expects` and D7 for survivors.
- The `red_proof` entries written into `_edad` gain `detected_by`, a list of node ids,
  beside the existing `command` and `exit_code`. A bare `{command, exit_code}` shape
  loses the FAILED/ERROR distinction the whole design rests on, which is the ground
  `gate.py` already rejects it on for `mutation_proof`.
- `Record.red_proof` carries those entries through unchanged; `evaluate` already copies
  the field out of the lock.
- `report_proof(rec)` reads the stored `detected_by`. An entry that has the field prints
  as a red proof under the current bar; a lock whose entries lack it prints as a
  pre-amendment import-only proof whose teeth were never verified. Never infer the tier
  from `exit_code` — that would classify the five existing locks for free while inventing
  a claim the run never recorded.
- The failure-key extraction feeding the ratchet (`extract_failure_keys`) must not be
  re-keyed. It folds `FAILED` and `ERROR` into one `pytest:<node>` shape, and those keys
  are persisted in every approval lock's `full_gate_baseline` — T002's current lock holds
  an ERROR-shaped key. Splitting them would make every stored baseline uncomparable and
  turn pre-existing failures into new ones. The new parsing is additive.

## Out of scope

- The mutation proof itself — **T003** (D1-D12), merged before this starts. This ticket
  reuses its detection functions and adds none.
- Migrating the existing locks. D19: the new bar binds new approvals only, and T001-T005
  keep the red proofs they recorded. They are hash-anchored evidence of what was actually
  run, and editing them to look compliant destroys the property that makes them worth
  having. Re-taking those proofs is unavailable in any case — the code now exists, so the
  commands come back green and the existing refusal catches them. Unenforced by
  construction: approve writes only the lock for the ticket being approved, so there is
  no behaviour to assert, only the absence of a migration step.
- Policing the pre-approve stub. D18: the gate cannot tell a signature skeleton from a
  near-complete implementation, because both are a diff inside `scope`, and a line-count
  or AST bound blocks a dataclass or a constant table while a determined author routes
  around it. Partly self-limiting — land enough implementation and the acceptance
  commands go green, which the existing bar refuses — but an author who lands most of it
  and leaves one bug gets a genuine `FAILED` that proves less than it appears to. A
  priced cost, not an oversight.
- Proving a red-tier test *asserts* on what it reached, rather than merely reaching it. A
  test that calls a `NotImplementedError` stub and asserts nothing still produces
  `FAILED`. Closing that needs the mutation tier, which D2 puts out of reach at approve
  time for greenfield, because a module that does not yet exist cannot be green at base.
- Re-running mutations at promotion — **D14**, unenforced.
- Verifying T001-T005's own frozen tests for teeth. Their modules now exist and are green
  at base, which makes them eligible for the mutation tier; five tickets of mutation
  authoring, deliberately not blocking this amendment. Owner: user.
