## Context

`approve` refuses a ticket whose acceptance commands already pass, on the grounds that
freezing a passing test proves nothing: either it asserts nothing, or the implementation
already exists. That is right for greenfield work and wrong for the central brownfield
test type. A characterization test pins existing behaviour so a refactor can be checked
against it, and it passes on day one by construction — passing is what makes it a
correct characterization. The only way past the refusal today is `--allow-passing`,
which stamps every downstream record `no red proof`.

Weakening the bar is not available. Passed-at-base plus passed-at-HEAD plus
diff-confined-to-scope is satisfied by a test that asserts nothing at all, so a green
proof is strictly weaker than a red one and must never be labelled equivalent.

What separates a real characterization test from a vacuous one is that a vacuous test
never runs, so the worst it can produce is a pytest `ERROR`. Only a test that actually
asserts something can produce `FAILED`. That distinction is the whole mechanism, and
`PYTEST_FAILURE_RE` currently discards it by folding both words into one key shape.

**Do not re-key the ratchet.** The keys `extract_failure_keys` produces are persisted:
every approval lock stores a `full_gate_baseline` of them, and `.edad/hashes/T002.json`
holds `pytest:tests/test_session_network.py` — itself an ERROR-shaped key. Changing that
key shape to carry the outcome would make every stored baseline uncomparable and turn
pre-existing failures into new ones across the whole repo. Add a second regex for
detection and leave `PYTEST_FAILURE_RE` and the keys alone;
`tests/test_gate_baseline.py::test_pytest_failures_key_on_the_node_id` pins the current
shape and runs in this ticket's `full_gate`.

## Goal

A ticket may declare a `mutation:` block: entries pairing a command that perturbs the
code being characterized with the frozen node ids that command is expected to trip.
`approve` runs each one in a throwaway worktree at HEAD and requires those exact node
ids to come back `FAILED`. Every acceptance command must be green at base first, and
`red_proof` stays null because none was taken.

The resulting contract is stronger than a red proof rather than a concession to it:
green against the code it characterizes, **and** dead in the declared places, under
every declared mutation.

## Required interface

Everything below lives in `edad/gate.py`. The frozen test asserts these names and
shapes; neither side can change.

- **`Mutation`** — a dataclass carrying `command: str` and `expects: list[str]`.

- **`mutation_entries(ticket: dict, allow_passing: bool = False) -> list[Mutation]`**
  Pure. Reads `ticket["mutation"]`, an optional list of mappings, and returns `[]` when
  it is absent or empty — that emptiness is what leaves an ordinary ticket ordinary.
  Otherwise every entry needs a non-empty `command` string and a non-empty `expects`
  list; anything else calls `die()` with a message naming `expects`. When the block is
  non-empty and `allow_passing` is true, `die()` with a message naming `--allow-passing`.

- **`detected_node_ids(output: str, frozen: list[str]) -> list[str]`**
  Pure, and runs nothing — the shape `frozen_blocks` established. Sorted, deduplicated
  node ids reported `FAILED` in one command's output whose file part (everything before
  the first `::`) is one of `frozen`. `ERROR` lines are never included, whatever they
  name, and a `FAILED` outside the frozen files is never included either.

- **`unfired_expectations(expects: list[str], detected: list[str]) -> list[str]`**
  Pure. The entries of `expects`, in declared order, that nothing in `detected` matches.
  A detected id matches an expected one on equality, or when the detected id is the
  expected id followed by `[` — so a base id is satisfied by its parametrised cases,
  while `<expected>_and_something_else` is not a match.

- **`remove_worktree(root: Path, path: Path) -> None`**
  Runs `git worktree remove --force <path>` and raises `subprocess.CalledProcessError`
  when git fails. A named module-level function because the frozen test replaces it —
  the same reason `docker_network_internal` is one.

- **`mutation_worktree(root: Path)`** — a `@contextmanager` yielding a `Path`.
  Creates a detached worktree at HEAD under `root/.edad/worktrees/`, named uniquely per
  call; that directory is already gitignored. Calls `remove_worktree` in a `finally`,
  and when that raises, `die()` with a message containing `str(path)`. Removal is forced
  because a bare `git worktree remove` fails on a dirty tree, which is the state every
  mutation leaves — the cleanup would fail in exactly the case it exists for.

- **`mutation_touched_paths(worktree: Path) -> list[str]`**
  Repo-relative paths from `git diff --name-only` inside the worktree.

- **`prove_mutation_or_die(root: Path, ticket: dict, commands: list[str]) -> dict`**
  The sibling of `prove_red_or_die`, and the only new caller of `run_commands`. In order:

  1. Refuse, naming the path, if any entry of `ticket["frozen"]` is untracked or dirty
     in `root`. The mutation runs against committed bytes, so a proof about text the
     lock does not hash is not a proof about the contract.
  2. Run `commands` in `root` through `run_commands`, passing the ticket's network
     denial, `declared_paths` and `command_timeout` exactly as `prove_red_or_die` does.
     Every command must exit 0; otherwise die naming each that did not. Nothing is
     mutated before this passes.
  3. Refuse, naming every acceptance command and the word `detection`, when none of them
     can supply it. A non-pytest command still runs and still must be green, but its
     exit code is never detection.
  4. For each entry from `mutation_entries`, inside its own `mutation_worktree`:
     1. Run the entry's `command` alone in the worktree. If it times out or exits
        non-zero, die naming the command — before any acceptance command runs there.
     2. Refuse, naming the stray path, if `mutation_touched_paths` yields anything
        matching none of `ticket["scope"]` under the existing `match_scope`.
     3. Run `commands` in the worktree. The mutation's detected set is the union of
        `detected_node_ids` across their outputs, and `acceptance_command` is the first
        command that contributed to it.
     4. Die naming the mutation command and every acceptance command that missed it when
        the detected set is empty.
     5. Die naming each id `unfired_expectations` returns when that list is non-empty.

  Returns `{"commit": <root's HEAD sha>, "green_at_base": [{"command", "exit_code"}, …],
  "mutations": [{"command", "touched", "expects", "acceptance_command", "detected_by"}, …]}`.

- **`cmd_approve`** — a ticket with a non-empty `mutation:` block takes the mutation path
  instead of the red one. `prove_red_or_die` is not called, the lock's `red_proof` stays
  `None`, and the `_edad` block gains `mutation_proof` holding what
  `prove_mutation_or_die` returned. `mutation_entries(ticket, args.allow_passing)` is
  what raises D12's error. Print the proof the way approve already prints the red one.

- **`Record`** gains `mutation_proof: dict | None = None`, placed so `asdict()` carries
  it into the record JSON.

- **`report()`** distinguishes three tiers where it prints two today. With a
  `mutation_proof`, print a line containing `mutation proof` and, on it or the next line,
  `<n> mutation` and `<m> distinct` — `n` the number of mutations, `m` the number of
  distinct node ids across every `detected_by`. It must not print `no red proof` in that
  case. A record with `red_proof` keeps its existing line and must not print
  `mutation proof`. A record with neither keeps the existing `no red proof` line.

## Out of scope

- **Generating mutations.** The gate runs what the ticket declares and never invents
  one (D1). Generated operators were rejected in the grill record for a heavy
  dependency, minutes-to-hours runtimes and a nondeterministic approve.
- **Re-running mutations at promotion** (D14, unenforced). The mutation is written
  against pre-refactor text and usually will not apply afterwards, so the check would
  abstain almost every time. `edad/session.py` is not in scope and is not touched.
- **Any second escape hatch.** No `--allow-undetected`. `--allow-passing` keeps its
  documented purpose and gains one error case (D12).
- **Enforcing the `## Widened scope` disclosure** (D13, unenforced). `scope` is a single
  allow-list, so a path added for editing and a path added for perturbing are
  indistinguishable to the matcher; it is `to-tickets` guidance and already landed in
  `.claude/skills/to-tickets/SKILL.md`.
- **A characterization ticket that uses this mechanism.** This ticket builds it and does
  not exercise it end to end. `legacy/mp3converter.py` is a two-line fixture with no
  ffmpeg call, so the obvious dogfooding target does not exist and the first real user
  would have to characterize `edad/gate.py` itself. That is a separate ticket and a
  separate decision.
- **Measuring coverage.** Nothing requires the declared mutations to span the behaviour
  the test claims to pin, and nothing here can check that. The mitigation is the shape
  line in `report()` (D11), which is disclosure rather than enforcement.

## Done when

Every command under `acceptance` exits 0, the frozen file hash is unchanged, and the
diff touches nothing outside `scope`.
